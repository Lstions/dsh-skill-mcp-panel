# 技能与 MCP 管理插件 — 需求清单

> 版本 v1 · 由 Lead 起草（依据本机实测与 DSH 源码事实），产品负责完善。
> 每条需求都必须是**可验证**的：能指出测试文件、命令与原始输出。
> 标 `[已实现]` 的是本轮之前就存在的功能，本轮只需回归，不得退化。

---

## 0. 这份清单要解决的问题

插件 `dsh-skill-mcp-panel` 目前已经把「多层分类技能发现」和「多技能根目录」做好了，
但**使用者仍然无法真正管理自己的技能与 MCP**：

1. 发现得到 139 个技能，却**一个都关不掉**——不想让模型看到的技能，只能去改技能文件或挪目录。
2. 出现同名技能时只有日志里一行警告，**界面上看不到冲突**，也不知道谁赢了、为什么赢。
3. 接 MCP 要手写 `cordis.patch.yml` 并重启，**界面上既看不到已配置的 server，也无法开关或改配置**。

本清单把这三件事变成可交付、可验收的需求。

---

## 1. 使用者与真实场景

| 角色 | 场景 | 现状痛点 |
|---|---|---|
| **A. 技能使用者** | 本机 3 个技能根、24 个分类、139 个技能 | 想临时关掉某些技能（如一次性迁移脚本类），没有开关 |
| **B. 排障者** | 某技能「明明存在却加载到别的版本」 | 冲突只在日志里，界面无信息 |
| **C. MCP 使用者** | 要接/关 MCP server、确认工具是否注册成功 | 必须手改 YAML + 重启；不知道 server 是否连上 |
| **D. 局域网使用者** | 通过 `http://100.64.0.10:3080` 访问 | DSH 在非 loopback 页面下禁用持久化 settings，配置卡是**空的** |

> **D 是硬约束**：DSH 平台在 `!isLoopback` 时把客户端 settings 持久化降级为 `memory`，
> 于是所有基于 `settingsScope` 的配置卡在局域网上都不可用（这是平台行为，我们改不了）。
> 因此本插件的管理界面**不得依赖 `settingsScope` 提供数据**，必须自带宿主 HTTP 通道。
> 这一条直接决定了下面的 N3。

## 2. 功能需求

### F1 分层多根发现 `[已实现]`

递归发现 `<root>/<分类>/<技能>/SKILL.md`，支持多个根目录。

**验收**：`test/run.js` 全绿；真实树测得 139 个唯一技能、24 个分类。

---

### F2 技能清单（可读、可定位）

在界面上列出当前**生效**的技能，每条至少包含：名称、描述、分类、来源根、SKILL.md 绝对路径、
provider、rank、是否可被模型调用、是否可被用户调用。

**验收标准**
- 列表条目数 == 宿主 `ctx.skills.list()` 的结果数（同一时刻、同一 scope）。
- 每条都能看到 `path`，且该路径真实存在于文件系统。
- 点开一条能看到完整信息；列表可按分类/根目录筛选，可按名称搜索。
- 139 条规模下页面可用（见 N5）。

---

### F3 开关技能（本轮核心）

**使用者预期**：在界面上把某个技能关掉，模型和用户命令都再也用不到它；打开就恢复。

**实现事实（决定了需求边界）**
- 技能注册表按 `[global, ...scope 层链]` 合并，**近层整体覆盖远层**；同层内按
  `rank → providerOrder → localOrder` 排序，**先到者胜**。
- 各 preset 把 `skill-filesystem` 注册进**它自己的 scope 层**。因此本插件（注册在 global 层）
  **无法压制**那些只在 preset 层里出现的同名技能。
- provider 只能**新增**候选，不能撤回别的 provider 已发布的候选。
  因此「关闭」的唯一可行机制是：**用同名候选赢下该名字**，并携带
  `invocation = { modelInvocable: false, userInvocable: false }`，同时 `get()` 返回
  `undefined`（使加载器拿不到正文）。
- **赢下名字的必然代价是该名字仍留在 `ctx.skills.list()` 中**（只是两个 invocation 标志为 false）。
  这不是缺陷，而是该机制的正确表现。实测证据：若改为「把自己的候选从 `list()` 省略」，
  等于**让出名字**，同层其他 provider 会立刻接手，使用者的「关闭」被静默无视 —— 见下方 F3.7。
- 所以「关掉」必须区分两种情况，且界面**必须如实显示**，不能假装成功。

**验收标准**
- F3.1 关掉一个**本插件独占**的技能后：
  1. `ctx.skills.list()` **仍包含**该名字（预期行为，非失败）
  2. 该条目的 `invocation.modelInvocable === false && invocation.userInvocable === false`
  3. `list().filter(isModelInvocable)` **不含**该名字 —— 这是对使用者真正有意义的观察
  4. `ctx.skills.get(name)` 返回 `undefined`
  5. `skill` 工具加载它时报 **"not available for model invocation"**
     （该文案正是本机制下的正确结果；报 "unknown" 说明名字已从目录消失，反而意味着压制方式不对）
- F3.2 打开后该技能重新出现，能与关闭前等价加载（内容一致）。
- F3.3 关掉一个**被别层/别 provider 抢走**的技能时，接口返回的该行
  `effective=false` 且 `shadowedBy` 指出仍在使用者列表里的那个 provider 名或原因；
  界面显示「已隐藏但未生效，仍由 X 提供」之类的明确文案，**不得显示为已关闭**。
- F3.4 开关是**持久**的：宿主重启后仍然生效（存在 settings 命名空间里）。
- F3.5 批量开关（如「关掉整个分类」）在一次写入里完成，返回逐条结果。
- F3.6 关闭只影响**可见性/可调用性**，**绝不修改或删除**技能文件本身。
  （测试必须断言 SKILL.md 的 mtime 与 md5 未变。）
- F3.7 **同层竞争者存在时，关闭仍必须生效。**
  构造两个同层 provider 提供同名技能，关闭后必须观察到：模型可见目录里没有该名字、
  `get()` 返回 `undefined`。
  这条是「赢下名字」机制相对「省略候选」的唯一优势，也是最容易被后人当成冗余
  「优化掉」的地方：一旦改成省略候选，本用例立刻变红。
  实测对照（Lead 探针）：
  ```
  赢下名字 : list=x<-nested-filesystem(model=false)  model可见=[]  get=undefined  => 关闭生效 YES
  省略候选 : list=x<-same-layer-competitor(model=true) model可见=[x] get=有正文  => 关闭生效 NO
  ```

### F4 冲突技能列表（本轮核心）

**使用者预期**：一眼看到哪些技能名被多个文件抢，谁赢了，为什么，我能不能改。

**验收标准**
- F4.1 列出所有同名多个候选的技能名，每条含：胜者（path/root/provider/rank）与
  全部落败者（path/root/provider/rank）。
- F4.2 与真实注册表一致：对每个冲突名，胜者的 `provider`+`path` 与
  `ctx.skills.list()` 里该名的实际值相同。
- F4.3 标出当前 `duplicatePolicy`，并说明该策略下用户可做什么
  （`first-wins`：靠 roots 顺序决定；`error`：该名字整个撤下）。
- F4.4 同一文件经两个根目录（符号链接别名）出现时**不算冲突**
  （本机 `.agents/skills` 是指向 `.hermes/skills` 的符号链接，必须只算一次）。
- F4.5 无冲突时显示「无冲突」而不是空白或错误。
- F4.6 `resolvable` 字段如实反映本插件能否改变该结果。

### F5 MCP server 清单与开关（本轮核心）

**使用者预期**：看到当前配置了哪些 MCP server、连上没有、各注册了多少工具，并能开关。

**验收标准**
- F5.1 列出**全部**来源的 MCP server：
  (a) 由本插件声明并挂载的；(b) 由 profile 的 `cordis.patch.yml` 等外部层插入的行。
  两类都要出现，且标出 `declared` 区分来源。
- F5.2 每行显示：serverName、transport、目标（命令行或 URL）、enabled、
  实时 `phase`、工具数、工具名列表。
- F5.3 能开关**可寻址**的已挂载行；结果显示三态：
  `applied` / `restart-required` / `refused`，并给出 `readOnlyReason`。
  **不允许把 `restart-required` 报成成功。**
- F5.4 工具数来自真实的工具注册表（`ctx.tools`），不是配置推断。
- F5.5 行不可寻址（如 `management-required`、`unaddressable`）时，开关必须禁用并说明原因。

---

### F6 MCP server 增 / 改 / 删

**使用者预期**：在界面上加一个 MCP server，填完就能用，不用手写 YAML，不用重启。

**验收标准**
- F6.1 支持 `stdio`（command/args/env/cwd）与 `streamable-http`（url/headers）两种 transport，
  字段与 `@deepseek-ai/dsh-mcp-client` 的 `Config` 一致（含 `toolCallTimeoutMs`、
  `failOnStartupError`、`reconnect`）。
- F6.2 `serverName` 必须是 MCP 合法模式（`^[A-Za-z0-9_-]{1,32}$`），
  重复名在提交时被拒绝并说明原因，**不写入**。
- F6.3 新增后：要么真实挂载成功（`applied`，且工具真的出现在 `ctx.tools` 里），
  要么如实返回 `restart-required` 并说明「重启后生效」。**不得谎报 applied。**
- F6.4 修改配置后按新配置重连；旧实例必须被正确 dispose（不残留工具）。
- F6.5 删除后该 server 的工具从 `ctx.tools` 消失。
- F6.6 声明持久化，宿主重启后仍在。
- F6.7 **降级**：当环境里没有 `@deepseek-ai/dsh-mcp-client` 时，
  界面显示明确说明（如「未安装 MCP 客户端」），而不是报错崩溃或假装可用。

> F6.3 的判定方式由开发在实现时**实测确定**并写入文档：
> 先试动态挂载（loader 解析模块 + `ctx.plugin()` 挂载），成功则 `applied`；
> 否则退回「写 patch + 提示重启」并报 `restart-required`。

**验收标准**

## 3. 非功能需求

### N1 中英双语（硬要求）
所有界面文案走 `ctx.locale`，`zh` 与 `en` 两个字典**键集合必须完全一致**。
不得出现硬编码的英文句子。

**验收**：两字典键集合相等的断言；切换 locale 后标题与关键标签真的变化。

### N2 视觉遵循 DSH 规范
- 只用主题令牌（`--dsw-*`），不写死颜色，亮/暗主题都正常。
- 折叠式卡片：默认收起，头部 `aria-expanded`，展开才渲染内容。
- 无内容时 `return null`（不渲染空壳）。
- 与「设置 → 插件」页现有卡片风格一致。

### N3 不依赖 loopback（硬要求）
管理页面的**数据通道**不得依赖 `settingsScope`：任何 `settingsScope` 不可用的页面
（含 `http://100.64.0.10:3080`）都必须能读状态、能操作。

**验收**：模拟 `settingsScope` 不可用（`available=false`）时，页面仍渲染列表并成功执行一次开关。
必须有一条测试**明确**覆盖这个场景。

### N4 安全
- 读接口**永不**返回密钥真值：含 token/secret/password/credential/authorization/api-key
  的键一律掩码；写回时掩码值代表「保持原值」，不得用掩码覆盖真密钥。
- 写接口要求同源 + `application/json`（阻断跨站表单类写入）。
- 提供 `writeAccess` 配置（`same-origin` 默认 / `loopback` 更严）。
- 端点不在 `/api` 下、无鉴权：README 必须**如实写明**这个限制与适用前提（可信局域网）。

### N5 性能
- 状态接口在本机 139 技能规模下 P95 < 500ms（预热后）。
- 列表首屏渲染不阻塞输入；分类折叠默认收起，避免一次渲染 139 行。
- 技能扫描不得每次请求都重新递归全树（要有失效与缓存）。

### N6 兼容与降级
- 没有 `pluginManager` 服务时：MCP 开关禁用并说明原因，其余功能正常。
- 没有 MCP client 包时：F6.7。
- 没有 `settings` 服务时：只读模式，界面说明。
- 不得修改内置 `skill-filesystem` 的行为，不得改 shipped preset。

---

## 4. 边界与非目标

- **不做**技能内容编辑（不改 SKILL.md 正文）。
- **不做**MCP 调用代理（不替用户执行 MCP 工具）。
- **不做**技能市场/下载。
- **不绕过** DSH 的 loopback 持久化门禁去改平台代码；只用自己的 HTTP 通道。
- **不承诺**能关掉所有技能：被近层覆盖的技能如实报告为未生效（F3.3）。

## 5. 验收证据要求

每条需求交付时必须给出：

1. **可指认产物**：需求编号 → 文件 → 测试用例名。
2. **原始输出**：自己跑过的命令与真实输出（不是汇总表）。
3. **变异自证**：关键门禁要做「改坏 → 必须红 → 恢复 → 哈希一致」。
4. **真实规模验证**：至少一项用本机真实技能树（139 技能 / 24 分类）跑出的数字。
5. **活体验证**：在运行中的宿主上验证（安装 + 实际调用一次）。
6. **未做的部分如实写**：不允许把「设计上支持」写成「已实现」。
